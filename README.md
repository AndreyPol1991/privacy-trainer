# Персональные данные и доступы — тренажёр аналитика

Двадцать одно задание на одном вымышленном сервисе записи к врачу: какие данные персональные, на
каком основании их собирают и сколько хранят, кто какие записи видит, где в проекте лежат секреты
и что писать в журнал действий. Отдельный раздел — про ИИ-ассистента в том же сервисе: куда
уходит обращение пациента, что хранить в журнале решений и как не смешать данные разных клиник.

Открывается двойным щелчком по `index.html` — ни сборки, ни сервера. Так же он раздаётся с
GitHub Pages и так же встраивается в платформу.

## Что внутри

| Раздел | Задания |
|---|---|
| Персональные данные | что считается персональными данными, основание обработки, срок хранения, сокращение состава |
| Модель угроз | кто нарушитель, какая мера от какой угрозы |
| Доступы | роль или признак объекта, матрица доступа, свои и чужие записи |
| Секреты | секрет или настройка, поиск секрета там, где его быть не должно |
| Аудит | журнал системы против журнала действий людей, состав записи аудита |
| Ассистент | что уходит во внешнюю модель, каналы утечки через ответ, разметку и журнал подсказок, мера против угрозы в точке пути данных, состав журнала решений и его полнота по цене ошибки, утечка между клиниками, модель изоляции, нужна ли особая защита обучения |

Форматы заданий: выбор одного, выбор нескольких, сопоставление, матрица «роль × действие», поиск
строк в журнале или схеме.
У части заданий есть лестница подсказок — раскрытая подсказка уменьшает вес доказательства,
но не обнуляет его.

Кроме заданий в каждом разделе есть интерактивы без оценки: объяснение «на пальцах», симуляторы и
прогоны. В разделе «Ассистент» — прогон обращения по пути «обращение → маскирование → поиск →
внешняя модель → проверка ответа → журнал», доска STRIDE с поправкой на ИИ, схема с мерами по
точкам пути и прогоном атак, конструктор журнала решений, пересмотр решения человеком, день двух
клиник на одном ассистенте и сравнение трёх моделей изоляции.

## Связь с платформой

Тренажёр отчитывается о решённых заданиях платформе T-shape, когда открыт внутри неё. Наружу
уходит только факт: код задания, номер успешной попытки и число раскрытых подсказок. Какой
индикатор графа навыков подтверждает задание — знает платформа, у неё лежит манифест. Это
сделано намеренно: привязка к модели оценки проходит ревью вместе с ней, а не меняется правкой
в этом репозитории.

Протокол `trainer/1`, сообщения через `postMessage`:

```
тренажёр → платформа   { protocol: 'trainer/1', trainer: 'privacy', kind: 'ready' }
платформа → тренажёр   { protocol: 'trainer/1', kind: 'hello', embedded: true, solved: ['pd-basis'] }
тренажёр → платформа   { protocol: 'trainer/1', trainer: 'privacy', kind: 'solved',
                         task: 'pd-basis', attempts: 2, hints: 1 }
платформа → тренажёр   { protocol: 'trainer/1', kind: 'accepted', task: 'pd-basis' }
```

Первое сообщение уходит всем (`*`): адрес платформы тренажёру неизвестен и меняется от стенда к
стенду. Дальше запоминается источник ответа, и всё остальное шлётся уже точно ему. В сообщениях
нет ничего, кроме кодов заданий.

Вне платформы тренажёр работает полностью: прогресс хранится в браузере, отчитываться просто
некому.

## Как добавить задание

1. Сначала — в платформе: строка в манифесте `apps/web/src/content/trainers/privacy.ts`
   (код задания, название, индикатор графа, тип доказательства, число ступеней подсказок).
2. Потом — здесь: запись в массиве `TASKS` с тем же кодом.

Порядок важен: задание, о котором платформа не знает, не засчитается — молча. Число подсказок
в двух местах должно совпадать: платформа не примет сообщение, где подсказок больше, чем указано
в манифесте.

Задания раздела «Ассистент» (коды `ai-…`) подтверждают навыки не только области D14
«Безопасность и данные людей», но и D16 «Функции на основе ИИ» и D12 «Архитектура и качества»,
поэтому в каталоге платформы у тренажёра должны быть заявлены и эти области.
